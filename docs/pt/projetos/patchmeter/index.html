PatchMeter.

Cruzo as linhas novas de um diff com a cobertura de testes para mostrar exatamente o que ficou sem execução.

Exemplo do projeto

Detalhes técnicos

Leitura do diff em Java
O parser em Java 21 registra a linha no arquivo alterado e sua posição no diff do Git. Isso permite localizar uma mudança sem cobertura mesmo após renomear o arquivo.
Leitura dos relatórios de cobertura
Um parser SAX lê o XML do JaCoCo e outro leitor processa LCOV. Uma linha adicionada com zero execuções entra na contagem de linhas sem cobertura. Se o relatório omite um arquivo selecionado inteiro, o resultado é inconclusivo.
Testes de regressão
Testes com JUnit exercitam diffs reais do Git com espaços e Unicode nos nomes, registros LCOV repetidos e cobertura parcial de desvios. Os testes MCP verificam a ordem das linhas entre páginas e detectam duplicatas.

O problema

Uma alteração pequena pode introduzir uma regra de negócio sem teste e mal mexer na porcentagem de cobertura do projeto. Durante a revisão, quero saber qual linha mudou e o que o relatório de testes registrou sobre ela.

Como funciona

O PatchMeter cruza o caminho e o número de cada linha adicionada no Git com registros do JaCoCo ou LCOV. O relatório diferencia execução, zero execuções e ausência de dados. Três consultas MCP permitem examinar o resultado por arquivo e linha.

O que o exemplo mostra

O exemplo sintético adiciona um desconto por quantidade. Das quatro linhas Java novas, duas foram executadas, a linha 7 do desconto teve zero execuções e a linha 8 ficou sem registro. A cobertura observada de 66,6667% fica abaixo do limite de 80%.

Limites da análise

O diff e o relatório precisam vir da mesma revisão do código. A porcentagem considera as linhas com registro explícito. Avaliar se as asserções verificam o desconto continua sendo parte da revisão.
